## 1. 研究问题与可否证命题

研究问题：一个技能库在历史 controller 下取得较高奖励后，把它接到继续训练过的 controller 上，是否保留相对优势？

零交互命题：在预先规定的任务分布和其他条件下，替换库的平均效应与 controller 无关：

\[
R(B_1,\theta_1)-R(B_0,\theta_1)
=R(B_1,\theta_0)-R(B_0,\theta_0).
\]

这个命题与“新技能一定有效”“部分回退一定有害”都不同。本实验允许得到零效应、同向主效应、交互但无伤害，或真正的有害迁移。只有事先定义的配对估计量和不确定性支持时，才使用负迁移一词。

## 2. 为什么需要四个状态，而不只比较两个 checkpoint

完整 checkpoint 随训练同时改变库与 controller。直接比较早期和晚期的两个 checkpoint，只给出联合变化的效果，无法辨认哪种状态贡献了变化。

最小静态评估矩阵：

| 单元 | 技能库 | 控制器 | 用途 |
|---|---|---|---|
| 00 | \(B_0\) | \(\theta_0\) | 早期配对基线 |
| 10 | \(B_1\) | \(\theta_0\) | 在旧 controller 下替换库 |
| 01 | \(B_0\) | \(\theta_1\) | 旧库与新 controller 的重组；类似部分回退 |
| 11 | \(B_1\) | \(\theta_1\) | 后期配对状态 |

\(B_0,B_1\) 和 \(\theta_0,\theta_1\) 必须来自可识别、实际保存的状态。`EvolutionSnapshot` 只含库而不含对应 controller，不能凭库快照重建 \(\theta_0\)。若没有可配对的完整 checkpoint，实验在“缺少状态证据”处停止；下一次经授权训练时增加保存时点，而不以猜测代替历史参数。

这是科学必要条件，不是新增的产品基础设施。现有完整 checkpoint 已具备保存 controller、optimizer 和 bank 的能力，优先复用它。

## 3. 选择状态，避免对测试集选赢家

在打开最终测试结果之前确定两种状态：

- 方案 A：一个事先指定的演化边界前后完整 checkpoint；适合检验一次具体技能变更。
- 方案 B：实现的训练奖励选择出的历史最佳库对应完整 checkpoint，以及之后某个预先规定的完整 checkpoint；适合检验实际部分回退语义。

二者可以各自成为独立实验，不能事后从许多阶段中挑出最强交互并只报告这一对。若使用历史最佳训练阶段，应保留它的选择规则、训练样本数、奖励窗口和所有候选阶段；最终测试数据不参与任何选择。

阶段平均奖励可能汇总多次 controller 更新后的反馈。必须事先指定取阶段开始、结束或某个已存在 checkpoint 的 controller，并记录该时点；不要把阶段均值称为这个单一静态配对已测得的性能。阶段得分用于选择，四格的实际测试分数另行取得。

对于一次库变化，记录哪些技能新增、修改、删除，保留修改前后文本与稳定身份。库变化若含多个同时修改的技能，本实验首先估计整个库更新的总效应，不把它归因到某一个技能。

## 4. 数据角色与泄漏排查

### 4.1 三种角色必须分别命名

1. **经验语料**：用于为每个单元重建具体 MemoryBank 的训练轨迹。
2. **训练反馈任务**：曾参与 controller 更新、designer 失败案例、阶段奖励或状态选择的任务。
3. **最终评估任务**：状态和阈值确定后才使用的任务。

ALFWorld 处理器在样本不足时可能让一次训练 A/B 分组重复或重叠。因此不能只记录“A”“B”两个标签；必须记录 game file、任务类型、来源 split、生成方式、实际重复次数及与最终评估任务的交集。

### 4.2 最终评估的分层

固定 train、in-distribution、out-of-distribution 文件清单和哈希；ID 与 OOD 分开报告。若同一模板家族形成高度相关的任务，按模板家族分组抽样/分析。至少核查 game file 的严格不相交；模板重叠及任务语义相似度属于更强的泛化边界，需单独说明，不能以文件不重名替代。

实际下载不到或来源不明的缓存不得用于主要比较。若必须使用已有缓存，另设探索性结果并注明其构建来源未知；不得把它与干净重建条件合并。

### 4.3 固定经验量

四格使用同一份经验轨迹，固定排序、可见字段与 token 预算。记录超过上下文预算的轨迹如何处理；当前 processor 按完整轨迹分块，不应默认为任意长度轨迹都被统一截断。若进行随机经验子采样，对四格使用同一组经验 ID，并按实际独立经验抽样批次区分不确定性。

## 5. 干预与运行控制

### 5.1 主要估计量：完整记忆构建路径

对每一个 `(bank, controller, experience_batch, evaluation_episode, seed)` 条件：

1. 从指定完整 checkpoint 提取并验证 controller；载入指定 bank。
2. 清空该单元的具体 MemoryBank 和构建缓存。
3. 用同一份经验语料，由这个 B/θ 配对独立构建记忆。
4. 对同一组最终评估任务执行检索与行动。
5. 保存技能选择、记忆变更、检索 IDs、行动序列、成功/失败和成本。

这个设计估计 B/θ 通过技能执行与具体记忆形成到最终行动的总效应。每格独立重建 M 是必要的：直接共享一个旧 M 会把要研究的主要作用路径冻结掉。

固定 M 可成为另一项辅助实验，但它不能被称为“控制器效应的更干净测量”，因为 controller 若只参与写记忆，固定 M 以后可能根本没有参与结果生成。必须先画出实际调用关系，才能定义这样的辅助估计量。

### 5.2 固定其他组件

明确固定并记录：记忆执行器和行动模型的具体 provider/model/version、嵌入模型及 revision、温度/top-p/seed、技能选择 K、memory retrieval K、chunk/overlap 策略、上下文预算、ICL 示例、最大行动步数、环境版本、任务随机性及缓存键。

不要直接照搬 train 与 eval 两个 shell 脚本的全部默认值作为“只有 B/θ 不同”的实验。所检查脚本在编码器、K 和其他参数上有差异，必须形成一个统一评估 manifest。

随机 seed 可以使运行更可复核，但无法保证远程模型完全确定。若有重复采样，应说明它估计的是同一任务上的生成波动，不能把多个 seed 当作多个独立任务扩大样本量。

### 5.3 兼容性检查

组合前检查 controller 的架构与编码器维度；核对 skill 名称、稳定 ID、技能顺序、操作表示与选择输出的映射。不同库含不同动作数时，必须使用实现支持的动态操作表示/合法掩码机制，防止把旧索引错误解释为新技能。不要为了凑成四格而修改 controller 结构。

保存一个人工可读的 `state_pairing.json`，记录每格 controller 文件哈希、bank 内容哈希、编码器和映射验证结果。状态无法兼容或映射存在歧义时，该格应标为不可评估；这本身是一项有信息的工程边界，但不是零分。

## 6. 观察量与判定标准

### 6.1 主要观察量

每个任务的成功指标是主要结果；固定任务集上的平均成功率为主要汇总。预先规定失败、超时、无效动作和 provider 错误的处理。基础设施错误不应自动解释为模型任务失败；须同时报告 intent-to-run 完成比例及可用的配对数。

四格完整配对是主分析集。若缺格，不将不同任务子集的均值当作可直接相减的四格交互。可以报告缺失机制与预先规定的敏感性上下界。

### 6.2 估计量

\[
\Delta_B(\theta_j)=R_{1j}-R_{0j},\quad
\Delta_\theta(B_i)=R_{i1}-R_{i0},
\]

\[
I=\Delta_B(\theta_1)-\Delta_B(\theta_0).
\]

- **库效应**：固定 controller 后更换库的平均变化。
- **controller 效应**：固定库后更换 controller 的平均变化。
- **交互**：库效应随 controller 改变的程度，尺度为成功率差。
- **排名反转**：两个 \(\Delta_B\) 的符号相反；还需分别报告不确定性。
- **负迁移**：在预先指定目标分布与固定 controller 下，新的库造成超过事先定义的实质伤害阈值的下降。

最小实质伤害阈值 \(\delta\)、置信水平、样本数与主要分层必须在结果出现前确定。可用预先可接受的实践差异而非结果最大化来选 \(\delta\)。当前没有执行预算和方差信息，不在本协议中编造样本量或承诺统计功效；拿到可用任务清单后，应根据配对不一致率或保守上界进行功效计划。

### 6.3 不确定性

使用按任务或模板家族的配对 bootstrap，并在每次 resample 中保留同一任务的四格与所有重复 seed。若采用 McNemar 检验，应明确二格配对的比较对象及独立性条件；它不直接代替四格交互分析。多分层、多阶段和多技能探索均标为探索性，并披露比较总数。

报告效应大小、区间、完整配对样本数、任务覆盖和预算；不要只用 p 值将结果切成“有效/无效”。区间跨越零时不等于两个系统等价；等价或非劣结论需要预先定义的边界与相应分析。

### 6.4 次要观察量

- 技能选择频率和分布差异；
- 具体记忆的写入、删除、更新及来源轨迹覆盖；
- 检索到的记忆 ID 与重复/冲突情况；
- token、调用量、行动步骤与运行失败；
- 类型、模板、ID/OOD 层面的效应异质性。

这些观察可以定位值得进一步测试的路径，但不会自动构成因果中介识别。若要声称“收益由某技能路由导致”，需要另行干预路由或技能，在适当条件下检验，而不只看路由与成功相关。

## 7. 如何区分竞争解释

| 结果模式 | 优先支持的解释 | 仍需保留的限制 |
|---|---|---|
| 新库在两 controller 下均改善且差异接近 | 库主效应占主导 | 区间精度可能不足以排除小交互 |
| 新 controller 在两库下均改善 | 路由学习可跨库迁移 | 仅限这两个库和该目标分布 |
| 匹配配对优于交叉配对，交互明确 | 存在共同适应/兼容性 | 具体由编码、选择还是记忆内容导致尚未分解 |
| 旧库在新 controller 下更差，但旧配对更好 | 历史奖励不适合直接评估重组状态 | 不说明普通部分回退设计在所有任务都错误 |
| 训练最佳配对在独立测试不领先 | 选择噪声、训练适应或分布差异值得继续检验 | 单次不领先不能辨明三者 |
| 重建缓存后差异消失 | 缓存来源/具体记忆路径是候选解释 | 若重建同时改变其他参数，不能作单因素归因 |

## 8. 扩展：静态重组和继续训练必须分开

主要实验只评估四种静态配对，不更新参数。若后续研究“回退后能否恢复”，需独立定义继续训练实验：

- 只恢复库、保留当前 controller/optimizer；
- 恢复匹配的完整历史 checkpoint；
- 保留当前全部状态。

为此还须控制 optimizer、RNG、采样器位置、失败案例池、designer 状态、训练剩余预算以及缓存。只恢复 controller 权重但保留不匹配 optimizer，不能称为完整历史恢复。某些状态能否完全恢复需再次核查执行路径和保存实际内容。

继续训练会引入适应速度与累计成本等新估计量；不要把静态四格与恢复训练后的结果混在同一个效应中。当前协议没有执行这项扩展。

## 9. 最小可复核材料

建议放入 AMS 现有研究目录中的一个小实验子目录，避免引入平台或新框架。至少保留：

- `protocol.md`：本协议及预注册的具体任务数、阈值和选择规则；
- `state_pairing.json`：四格文件身份、配置与映射核查；
- `dataset_manifest.json`：经验/训练反馈/最终评估 ID、哈希、交集检查、来源；
- `runs.jsonl`：逐任务四格结果、seed、memory 与检索记录引用、错误；
- `analysis.py`：配对效应、分层和区间生成；
- `results.json`：真实执行后才生成的统计结果；
- `receipt.json`：commit、环境、时间、执行命令、文件摘要、provider 身份与成本范围。

对于敏感数据或不具备再分发权的数据，只发布允许公开的 ID/哈希、聚合结果与生成方法，不将原始内容擅自复制进公共仓库。若没有可用公开数据，保持协议状态即可；不得用人造标签替代真实模型能力实验。

## 11. 本轮结论

本协议的贡献是把“回退后是否仍是最佳库”转成可区分的状态干预。真实负迁移、共同适应的存在与大小、任何最终导出策略的优劣，均未由本轮实验确认。
